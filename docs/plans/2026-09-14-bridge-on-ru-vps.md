# Мост на российском VPS (вариант 1)

## Зачем

Тест [2026-09-13-max-sms-ab-auth-test.md](2026-09-13-max-sms-ab-auth-test.md)
показал: авторизация MAX с российского выхода проходит с первого запроса,
с зарубежного — SMS не приходит. Владелец выбрал вариант с минимумом
переделок: мост запускается на том же российском VPS, где уже получен
рабочий пропуск (session), в режиме staging (только наблюдение).

Известный принятый риск: Telegram из России работает ненадёжно (тот же VPS,
фотобот уже сталкивался). Если мешает — переезд на вариант 2 (мост за
границей + российская дверь для MAX) дёшев: код один и тот же, меняются две
настройки.

## Что где сейчас

| Место | Что есть |
|---|---|
| Зарубежный сервер | старый staging-каталог моста, **остановлен**; старые `.env.staging*`, `config.local.staging.yaml`, `data.staging/` (старый нерабочий session) |
| Российский VPS | PokerLynx, фотобот (чужие проекты, не трогать); `/opt/maxgram-auth-test` — код commit `3f8e815`, образ auth-test, том `max_sms_auth_test_session` с **рабочим** `session.db`, приватный `auth-test.env` |

Адреса и реквизиты серверов в документы и Git не заносятся.

## Готово, когда

- на российском VPS в отдельной папке `/opt/maxgram-bridge` собран образ моста из `dev` (commit `3f45640` или новее);
- в `data.staging/` лежит `session.db`, скопированный из тома auth-test, владелец UID 10001;
- мост запущен один раз в staging-режиме (`restart: no`, `OUTBOUND_ENABLED=false`) и в журнале видно успешный вход по сохранённому пропуску **без** `AUTH_REQUEST`;
- владелец получил в личку от бота служебное сообщение о запуске (heartbeat/статус) — это наблюдаемый признак «Telegram из России работает»;
- входящее сообщение из разрешённого MAX-чата появилось в Telegram-форуме.

## Не трогать

- контейнеры, тома, папки PokerLynx и фотобота;
- том `max_sms_auth_test_session` (только читать — копия из него, не перенос);
- код: `device_type`, `app_version`, auth-flow, egress-логика — правок кода в этой задаче нет;
- firewall, sshd, глобальные настройки Docker;
- зарубежный сервер — ничего не запускать, старый session оттуда не переносить.

## Стоп-гейты

1. **Мост не запускать, пока `session.db` не скопирован и не проверен.** У
   моста нет своей защиты от запроса SMS: без пропуска он сам сделает
   `AUTH_REQUEST` (исправление `03c8387` лишь останавливает цикл при лимите).
2. Первый запуск — только `docker compose run`/`up` без `-d` с наблюдением
   журнала. Появилась строка про `AUTH_REQUEST`, `requesting sms code` или
   `max_auth_rate_limited` → немедленно остановить, не перезапускать, доложить.
3. Постоянный запуск (`restart: unless-stopped`, prod-compose, watchdog) —
   только отдельным решением владельца после успешного staging-наблюдения.
4. `OUTBOUND_ENABLED` остаётся `false` (Telegram → MAX выключен) до отдельного ОК.

## Как выполняется (механика)

Исполнитель не имеет SSH на сервер (блокируется защитой Claude Code);
рабочая схема из теста 14.09: исполнитель пишет `D:\tmp\*.ps1` (латиница,
без `&&`) + `D:\tmp\*.sh` для серверной части, владелец запускает одну
строку `powershell -ExecutionPolicy Bypass -File D:\tmp\<имя>.ps1` и
присылает последние строки вывода. Секреты владелец вводит через `Read-Host`
в своём окне, они уходят по SSH в файл с правами 600 и в чат не попадают.

## Блоки

### Блок 1 — код и образ (без запуска)

1. `git archive` текущего `dev` → `D:\tmp\maxgram-bridge-<commit>.tar.gz`
   (в архив попадают только файлы из Git, секретов там нет).
2. На сервере: `/opt/maxgram-bridge`, распаковать, `docker compose -p maxgram-bridge-staging -f deploy/docker-compose.staging.yml build`.
3. **Проверяемый результат:** образ собран, `docker ps -a` без контейнеров `maxgram-bridge-*`.

### Блок 2 — настройки (владелец вводит сам)

1. Из шаблона `deploy/staging.env.example` собрать `.env.staging` (ID владельца, ID форум-группы, разрешённые пользователи, username бота) и `.env.staging.secrets` (токен бота, телефон). Ввод — `Read-Host` в окне владельца; на сервере права 600.
2. `config.local.staging.yaml`: список разрешённых MAX-чатов (`chats:`), egress оставить **`hetzner_direct`** из `config.yaml` — это тип `direct`, для российского VPS правильно; имя профиля историческое, код не менять. Известная косметика: `/status` покажет предупреждение «non-RU direct egress» — оно ложное на этом сервере, принять как есть.
3. **Проверяемый результат:** команда печатает только имена ключей файлов (`cut -d= -f1`) и число строк; значения не выводятся.

### Блок 3 — пропуск MAX

1. Скопировать `session.db` из тома `max_sms_auth_test_session` в `/opt/maxgram-bridge/data.staging/` (через временный контейнер с `-v`, том монтировать **только для чтения**), `chown 10001:10001`, права 600.
2. **Проверяемый результат:** файл есть, размер > 0, владелец 10001. Дополнительно — один прогон auth-test в режиме `reuse` с подменой тома на `data.staging` (без новой авторизации по конструкции): ожидаем `session_reuse success=True auth_request_count=0`.

### Блок 4 — первый запуск (только по команде владельца «запускай мост»)

1. `docker compose -p maxgram-bridge-staging -f deploy/docker-compose.staging.yml up` (без `-d`), владелец наблюдает журнал ~2–3 минуты.
2. Хорошие признаки: вход по сохранённому пропуску, heartbeat в личку Telegram, нет строк из стоп-гейта 2.
3. Остановка `Ctrl+C`; **проверяемый результат** — выдержка журнала без секретов и скриншот сообщения бота в Telegram.

### Блок 5 — закрытие

Шапка плана → «реализовано» с датой и признаками; `docs/environment-inventory.md` — строка про новую площадку без адреса; решение «вариант 1» — в `docs/decisions/`, если там ведётся реестр. Постоянный запуск — отдельный план.

### Грабли (для следующего раза)

- `config.local.staging.yaml` и `config.yaml` монтируются в контейнер и
  читаются пользователем UID 10001: режим `600 root:root` даёт
  `[Errno 13] Permission denied` и мост падает на старте. Верно:
  `chown 10001:10001` + `chmod 400` для локального конфига, `444` для
  `config.yaml`. Файлы `.env*` читает docker compose на хосте — им 600.
- Том auth-test называется `max-sms-auth-test_max_sms_auth_test_session`
  (Compose добавляет имя проекта), не `max_sms_auth_test_session`.
- PowerShell 5.1: `%d` в строке ломает разбор — форматирование выносить в
  `.sh`; ps1 держать на латинице и без `&&` (урок 14.09).
- `TG_FORUM_GROUP_ID` был введён вручную без ведущего минуса (13 знаков
  вместо 14) → Telegram отвечал `Bad Request: chat not found` на создание
  темы, мост писал `topic_create_failed` / `no_topic`. Диагностика:
  `getChat`/`getChatMember` с токеном из файла на сервере (значения не
  выводятся); реальный ID группы — через `getUpdates` при остановленном
  мосте (иначе он забирает события первым). Правило: ID форума проверять
  `getChat` до первого запуска, значения из ссылок `t.me/c/<n>` — всегда
  с префиксом `-100`.
- Бот-администратор без права «Управление темами»
  (`can_manage_topics: False`) не сможет создать тему под MAX-чат.
  Проверять `getChatMember` до запуска; право выдаётся в Telegram без
  перезапуска моста.

### Ответы Telegram → MAX включены (2026-09-14, решение владельца)

`OUTBOUND_ENABLED=true` в `.env.staging`; значение подставляется в Compose
через `--env-file .env.staging` (надстройка `persist.yml` читает
`${OUTBOUND_ENABLED:-false}`). Проверено сквозным сообщением из темы
«Родители 1 "П"» с ведущим `@TG_Max_ConnectorBot`: реакции 👀 → 👍, текст
появился в группе MAX. Правила отправки — только из темы форума, только
разрешённый пользователь, только с упоминанием бота в начале
(`outbound_policy.py`).

**Канонические команды на сервере** (без `--env-file` Compose подставит
`OUTBOUND_ENABLED=false`):

```bash
cd /opt/maxgram-bridge
# перезапуск / применение настроек
docker compose --env-file .env.staging -p maxgram-bridge-staging \
  -f deploy/docker-compose.staging.yml -f deploy/docker-compose.staging.persist.yml up -d
# остановка
docker compose --env-file .env.staging -p maxgram-bridge-staging \
  -f deploy/docker-compose.staging.yml -f deploy/docker-compose.staging.persist.yml down
```

Сообщения в группы MAX, отправленные пока мост остановлен, не догоняются
(history sweep есть только для DM) — перезапуски планировать в тихое время.

### Правки по замечаниям владельца (2026-09-14, вечер)

Все три — с зелёным прогоном `473 passed` и установлены на работающий мост.

1. **Вид сообщений.** Вместо `[Написано напрямую в MAX]` / `[Имя]` —
   `🟢 Вы: ` и `👤 Имя: ` (`message_context.sender_prefix`). В DM чужие
   сообщения без подписи: собеседник назван в заголовке топика. У медиа без
   текста двоеточие снимается. Жирный шрифт не вводился: мост шлёт текст без
   `parse_mode`, включение потребовало бы экранирования во всех точках
   отправки.
2. **Реакции MAX больше не затирают текст.** Было: `_on_max_reaction_update`
   вызывал `edit_message_text` и заменял текст сообщения строкой счётчиков —
   сообщение в Telegram превращалось в «👍 1». Стало: реакция ставится
   реакцией (`set_message_reaction`). Правка текста невозможна в принципе —
   Telegram требует полный текст, а plaintext не хранится (privacy first).
3. **Ответ больше не выдаётся за пересылку.** `_extract_forwarded_payload`
   считал пересылкой любой `link.type != "REPLY"`, поэтому ответ с цитатой
   приезжал как «↪️ Переслано из MAX» с текстом цитируемого вместо ответа.
   Введён `FORWARD_LINK_TYPES = {CHANNEL, FORWARD, FORWARDED}`; всё
   остальное — связь внутри чата.

**Пометка удаления** (`mark_removed_message_in_topic`): MAX присылает
удаление как то же сообщение со статусом REMOVED; мост находит копию по
базовому `max_msg_id` и отвечает на неё «❌ Это сообщение удалено в MAX».
Проверено владельцем в DM. Редактирование копии не подходит — стёрло бы
текст.

- **Реакции MAX → Telegram не приходят.** Подписка есть и в PyMax 2.4.1
  (`Client.on_reaction_update`), и в мосте, но за 15 минут наблюдения от MAX
  пришли только `opcode=49 CHAT_HISTORY`; ни одного события реакции.
  Правка (2) корректна и сработает, если событие появится. Обходной путь —
  дифф по периодическому опросу истории — дорог (состояние по каждому

### Поздний вечер 14.09: реакции Telegram → MAX, тихий старт, второй пользователь

- **Реакции Telegram → MAX сделаны** (`476 passed`). Цепочка:
  `Dispatcher.message_reaction` → `TelegramAdapter._dispatch_message_reaction`
  (deny-by-default: своя группа, разрешённый пользователь, outbound включён)
  → `BridgeCore._on_tg_reaction_action` (связка через `tg_reply_map`) →
  `MaxAdapter.set_reaction` → `Client.add_reaction/remove_reaction` PyMax.
  Снятие реакции переносится; MAX на снятие отвечает пустым телом, это успех.
- **Две грабли по дороге.** (1) Telegram шлёт `message_reaction` только по
  явному `allowed_updates` и **запоминает набор на своей стороне**; в коде
  было два `start_polling`, реальный — в `startup/composition.py`, и правка
  в `TelegramAdapter.start()` ничего не меняла. Проверка:
  `getWebhookInfo.allowed_updates`. (2) Живой клиент PyMax лежит в
  `state.connection.client.raw_client`, а не в `backend`; без него
  `set_reaction` молча возвращал False — теперь причины пишутся в журнал
  (`max.reaction.skipped/failed`).
- **Уведомление «Maxgram запущен»** в личку отключено по решению владельца
  (`startup/composition.py`); сообщения о сбоях/восстановлении остаются.
- **Второй разрешённый пользователь** добавлен в `TG_ALLOWED_USER_IDS`
  (`.env.staging`, значения в репозиторий не заносятся): до этого её
  сообщение с корректным упоминанием бота отбрасывалось молча — так и
  задумано (deny-by-default), но владельцу это было неочевидно.
  Правило: новый участник семьи = его Telegram user id в список + `up -d`.
- Переименование темы в Telegram на работу не влияет: связка по
  `tg_topic_id`. Удаление темы — влияет (мост шлёт в никуда).

### Отложенные сообщения — кодом закрывать не нужно (проверено 14.09)

Штатная отложенная отправка Telegram («зажать отправку → Отправить позже»)
даёт то, что нужно: Telegram доставляет сообщение в топик в назначенное
время, бот видит его как обычное входящее и пересылает в MAX. Упоминание
`@бот` в начале в отложенном сообщении сохраняется, поэтому
`authorize_outbound_message` пропускает его. Проверено владельцем на живом
сообщении (запланировано, отправлено, доехало в MAX).

Отдельная реализация (`/через 2ч`, `/в 9:00`, очередь в БД, `send_at` у
PyMax) **не требуется**. Важно: отложенные сообщения живут на серверах
Telegram и боту до отправки не видны — показать их в MAX заранее
невозможно в принципе.
